# CLI login moves to the OAuth device authorization grant

Date: 2026-10-02. Status: planned, not started. Revised 2026-10-03 after review (the review's findings are folded into the text below; the as-executed section stays empty until Milestone 1 runs).

`tiddly login` signs the user in with Clerk's OAuth 2.0 Device Authorization Grant (RFC 8628): the CLI prints a short code and a URL, opens the browser to Clerk's hosted approval page with the code prefilled, and polls Clerk's token endpoint until the user clicks Approve. This replaces the authorization-code-with-PKCE flow that listens on a loopback port for a browser redirect. The device grant is the only interactive login. `tiddly login --token bm_...` (Personal Access Token) is unchanged and remains the path for CI and scripts.

## Why

The loopback flow needs the browser and the CLI on the same machine. Over SSH into a remote box, `tiddly login` opens nothing the user can see and waits out a five-minute timeout, so remote users have had to mint a PAT in the web app instead. The migration ledger (`docs/auth0-clerk-ledger.md`, "CLI auth: device authorization flow") records this as the headline capability lost when Tiddly moved from Auth0 to Clerk in July 2026, with the note "If Clerk ever ships device flow, this entry should be updated." Clerk shipped it on 2026-09-08.

With the device grant the browser can be on any device, so SSH and container logins work interactively. On a desktop the cost is one Approve click per login (the loopback flow was hands-free after a one-time consent). `tiddly login` runs about once per machine, so that cost is a click per machine. That rests on Clerk's documented statement that OAuth refresh tokens never expire (a docs claim; the ledger's Q2 records it as not exercised). Two things do force an extra login: `tiddly logout`, and replaying a rotated-out refresh token, which the ledger observed revokes the whole grant.

## Decided

- **Device grant is the only interactive flow.** The loopback flow, its listener, its `state` correlation, and its tests are deleted. Keeping both flows was considered and rejected: it needs a flag plus an environment heuristic to pick a flow, and the obvious heuristic (the browser-open command failing) does not fire over SSH into a workstation, where `open` or `xdg-open` exists and starts successfully.
- **The CLI always prints the URL and the code before opening the browser.** The printout is the no-browser path (SSH, containers: the user opens the short URL on any device and types the code) and the self-check when entering the code by hand, so the user approves their own request and not a stale page. It is not a phishing defense: the auto-opened page has the code prefilled and nobody compares anything. Suppressing the printout for tidiness removes the SSH path.
- **Link phishing is an accepted, recorded change.** RFC 8628 §5.4: an attacker can start a device flow for the "Tiddly CLI" client and send a victim the prefilled approval link outside any CLI session; if the victim approves, the attacker holds the victim's tokens. The defense is Clerk's hosted consent page, which names the application and its scopes with equally visible Approve and Deny actions. The loopback flow was not exposed this way (its authorization code landed on the victim's own machine). The ledger addendum in Milestone 3 records this as knowingly accepted.
- **Hand-rolled polling, not `golang.org/x/oauth2`.** That package implements RFC 8628 (`Config.DeviceAuth`, `Config.DeviceAccessToken`) and the CLI does not import it today. Using it would need a custom `Transport` for the mandatory `User-Agent`, unwrapping of `*oauth2.RetrieveError` to produce the per-code messages below, and a new dependency, all to replace about 80 lines. Not worth it.
- **`pkce_required` stays `true` on the existing "Tiddly CLI" application; it is never turned off.** The authorization-code flow stays live on that application until every old binary has been retired (Milestone 4 step 6), and `pkce_required` is the server-side enforcement for that flow. Turning it off would weaken a flow real users are still on for the whole upgrade window. Clerk's docs scope the setting to authorization requests, and the device grant makes none, so a rejection is unlikely. If Milestone 1 shows one anyway, the answer is a second OAuth application for the device grant (see Milestone 1 step 4), not a downgrade of the first.
- **No SSH detection to skip the browser-open attempt.** `DefaultBrowserOpener.Open` starts the command with no stdin or stdout, and Go connects unset child streams to the null device, so a text browser that `xdg-open` falls back to gets no terminal and exits. The attempt is harmless over SSH and the printed URL covers that case.
- **No backend change.** The device grant issues the same Clerk OAuth access tokens (`typ: at+jwt`, `client_id` claim, 24 h lifetime) and rotating refresh tokens as the authorization-code flow, from the same "Tiddly CLI" OAuth application and client ID. Milestone 1 proves this on the dev instance instead of trusting Clerk's changelog.
- **Keyring storage, the token resolution chain, and refresh handling stay as they are.** The stored credential accounts do not change, so a user who upgrades the CLI keeps their existing login. The one exception is the second-application branch of Milestone 1 step 4: a refresh token is bound to the client that issued it, so if the new binary ships with a new client ID, an upgrading user's first refresh fails with `invalid_grant` and the existing "session expired, run `tiddly login`" message. One forced login per machine in that branch, recorded in the changelog entry if it happens.
- **Scopes stay `openid profile email offline_access`.** `offline_access` is what makes Clerk issue a refresh token.
- **Every Clerk configuration change is an operator step: show the exact command, wait for approval, then run it.** Production changes are approved one at a time. The implementing agent never changes a Clerk setting on its own, including when a probe fails because of one.
- **Out of scope:** Client ID Metadata Documents for the MCP servers, and cleanup of the dynamically registered OAuth applications in Clerk. Both are separate decisions.

Clerk advertises these only when the feature is available on the instance and the verification page is reachable, so no support request is needed.
- The hosted verification page exists at `https://accounts.tiddly.me/device` (it redirects to sign-in and back, checked in a browser). It lives in Clerk's Account Portal, which must stay enabled. The page bot-blocks non-browser clients: `curl` gets a 403 under both a `tiddly-cli` and a Chrome user agent (checked 2026-10-03), so no probe or liveness check may fetch it; check it in a real browser.
- With the grant disabled, `POST https://clerk.tiddly.me/oauth/device_authorization` with the CLI's client ID and scopes answers HTTP 400 and the body `{"error":"invalid_grant","error_description":"The provided authorization grant ... is invalid, expired, revoked, does not match the redirection URI used in the authorization request, or was issued to another client. The requested OAuth 2.0 Client does not have the 'urn:ietf:params:oauth:grant-type:device_code' grant."}` (checked 2026-10-03). The error code is the same `invalid_grant` that means "expired or already used" during the token poll, so the device authorization step must not share the poll's `invalid_grant` mapping. See the conventions and Milestone 2 step 2.
- The "Tiddly CLI" OAuth application on both instances has `device_authorization_grant_enabled: false`, `pkce_required: true`, `public: true`, scopes `email offline_access openid profile`, redirect URI `http://127.0.0.1/callback`.
- The dev instance's authorization-server metadata was not checked. Milestone 1 checks it.
- Whether Clerk rejects device requests from an application with `pkce_required: true` is undocumented. Clerk's docs say the device grant "does not use redirect URIs or PKCE" and describe `pkce_required` as rejecting authorization requests that omit PKCE, which the device grant never sends. Milestone 1 settles it; the production probe above is inconclusive because the grant-disabled error fires first.

## Conventions shared by every milestone

- **Endpoints**, relative to the OAuth issuer (`OAuthConfig.Issuer`, `https://clerk.tiddly.me` in production, overridable with `TIDDLY_OAUTH_ISSUER`): `POST /oauth/device_authorization` and `POST /oauth/token`. Both are form-encoded and both must carry the CLI's `User-Agent` (`tiddly-cli/<version>`), because Clerk's endpoints answer default HTTP-library user agents with a bare 403.
- **Device authorization request:** `client_id` and `scope`. Public client, no secret.
- **Token poll:** `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, `client_id`.
- **Device authorization errors:** any non-200 from `/oauth/device_authorization` ends the login with a message saying the OAuth application may not have the device authorization grant enabled, followed by Clerk's `error` and `error_description` verbatim. This includes `invalid_grant`, which is what Clerk returns for a disabled grant (see "Current state"). The "may" is deliberate: the same path also carries `invalid_client` (wrong client ID) and the bare 403 from a missing `User-Agent`, and the verbatim description tells those apart. The poll's `invalid_grant` mapping below never applies at this step.
- **Polling rules (RFC 8628 §3.5, Clerk's docs):** wait `interval` seconds between polls (default 5 if absent or zero: Go cannot tell an absent field from a zero, and a zero interval would be a tight loop); on `authorization_pending` keep polling; on `slow_down` add 5 seconds to the interval and keep polling; on `access_denied` stop with "access denied"; on `expired_token` or `invalid_grant` stop and tell the user to run `tiddly login` again; on any other error stop and show the error. Stop at `expires_in` seconds (default 600 if absent or zero) even if the server never says `expired_token`. A `device_code` can be exchanged once.
- **Sleep and clock are injectable; durations are never scaled.** The flow has two fields: `Sleep func(ctx context.Context, d time.Duration) error`, whose default selects on `time.After(d)` and `ctx.Done()` and returns `ctx.Err()` on cancellation, and `Now func() time.Time`, defaulting to `time.Now`. `Login` computes the expiry deadline once as `Now()` plus `expires_in`, then loops: `Sleep(ctx, interval)` (plus any `slow_down` increments), check `Now()` against the deadline and stop with the expiry message if passed, then poll. Sleep first, so the first poll is never immediate and no poll is sent after expiry. Tests substitute a `Sleep` that records each requested duration and returns at once (or returns `ctx.Err()` for the cancellation test) and a `Now` that advances a fake clock, so the assertions are exact (`[5s, 5s, 10s]`) and instant, with the RFC numbers unscaled in the code. Production never sets either field. A time-scaling knob was considered and rejected: a test that measures wall-clock gaps at millisecond scale flakes on loaded CI runners, and a production duration multiplied by a test-only field is a latent bug with no guard.
- **Every request carries the command's context.** `postForm` takes a `ctx` and builds the request with `http.NewRequestWithContext`, so Ctrl+C interrupts an in-flight device authorization or poll request instead of waiting out the client's 10-second timeout. The context carries cancellation only; expiry is the `Now()` check above, not a context deadline (two clocks would disagree under the fake `Now`, and the client timeout already bounds a single request). After a 200 from the poll, `Login` checks `ctx.Err()` and discards the tokens if the user cancelled while the response was in flight, so a cancelled login never stores credentials.
- **Clerk configuration commands** use the Clerk CLI: `clerk api /oauth_applications/<id> --instance <dev|prod> -X PATCH -d '{"device_authorization_grant_enabled": true}'`. Application IDs and the dev client ID live in the operator's private note and local env, never in the repo. The pattern established in the migration plan: show the command, get approval, run, then read the setting back to confirm.

## Milestone 1: prove the device grant on the dev Clerk instance

### Goal and outcome

Confirm, on the dev instance and before any CLI code changes, that the "Tiddly CLI" OAuth application can issue tokens through the device grant and that the backend accepts them unchanged.

- The dev instance advertises the device endpoint, or the reason it does not is recorded.
- The dev "Tiddly CLI" application has the device grant enabled.
- One scripted probe gets a device code, is approved in a browser, and receives an access token and a refresh token.
- The access token is a JWT with `typ: at+jwt`, a `client_id` claim equal to the dev CLI client ID, and a `sub`. The local API (running against the dev Clerk instance, the established local real-auth setup) answers `GET /users/me` with 200 for it.
- The refresh token works at `/oauth/token` with `grant_type=refresh_token` and returns a rotated pair.
- The `pkce_required` question is answered and recorded, and `pkce_required` is still `true` on the existing application at the end of the milestone.

### Implementation outline

This is an operator milestone with a probe script. No CLI code changes.

1. Fetch `<dev issuer>/.well-known/oauth-authorization-server` and confirm `device_authorization_endpoint` is present. If it is absent, stop and report: Clerk advertises it only when the feature is available and the verification page is reachable, which usually means the Account Portal is disabled on dev. Check the dev verification page in a browser, never with `curl` (it bot-blocks non-browser clients; see "Current state").
2. Operator step, show and approve: enable `device_authorization_grant_enabled` on the dev "Tiddly CLI" application. Read it back.
3. Write the probe as a rerunnable shell script (not committed, keep its output in the as-executed notes): request a device code with the CLI's `User-Agent`, print `user_code` and `verification_uri_complete`, poll `/oauth/token` every `interval` seconds while the operator approves in a browser, then decode the access token's header and payload.
4. If step 3's device authorization request fails with an error that names PKCE, that is the undocumented interaction. Do not patch `pkce_required` (see "Decided"). Instead, operator step, show and approve: create a second OAuth application on dev, "Tiddly CLI (device)", with `public: true`, `device_authorization_grant_enabled: true`, the same four scopes, no redirect URI unless Clerk's API requires one, and `pkce_required` left at its default. Re-run the probe with the new application's client ID and record the outcome. The consequences of this branch, all recorded in the as-executed section: Milestone 2 ships the new production client ID in `DefaultOAuthConfig` (created in Milestone 4 step 1) and the dev override value changes; upgrading users get one forced re-login (see "Decided", keyring bullet); Milestone 4 step 6 deletes the old application instead of trimming it. If step 3 succeeds with `pkce_required: true`, record that and the second application is never created.
5. Call the local API's `GET /users/me` with the access token. Then exchange the refresh token once and confirm a new pair comes back.

### Definition of done

- The as-executed section of this plan records: the dev metadata check, the exact PATCH commands run and their read-back, the probe's device authorization response (codes redacted), the decoded token header and payload (`sub` redacted), the API response status, the refresh result, and the `pkce_required` answer (including, in the second-application branch, the creation command, the new application's settings read back, and the dev client ID's location in the private note).
- A copy of the probe script's command lines is in the as-executed section so a reviewer can rerun it.
- If anything above fails, the milestone is not done and the failure is recorded instead of worked around.

## Milestone 2: replace the CLI login flow

### Goal and outcome

`tiddly login` signs in with the device grant against Clerk. Everything else about the CLI's credentials is unchanged.

- Running `tiddly login` prints a URL and a short code, opens the browser to the code-prefilled approval page, waits, and on approval stores the access and refresh tokens in the same keyring accounts as today, then prints "Logged in as <email>".
- The same command works from a machine with no browser: the user opens the printed URL on any device, enters or confirms the code, approves, and the terminal completes.
- If the browser cannot be opened the CLI says so and keeps waiting. The printed URL and code are always shown first.
- Denying in the browser, letting the code expire, pressing Ctrl+C, and Clerk error responses each end the command with a specific message. The expiry and `invalid_grant` messages say to run `tiddly login` again; `--token` is mentioned only in the command's help as the CI path, not as a fallback for a failed interactive login.
- A login attempt against an OAuth application that does not have the device grant enabled fails at the first request with a message that names that setting, because this is the exact misconfiguration a new instance or an out-of-order production rollout produces.
- Pressing Ctrl+C while a request is on the wire returns within the same second, not after the HTTP client's timeout, and never stores tokens.
- Token refresh, `tiddly auth status`, `tiddly logout`, and `tiddly login --token` behave as before. A user who upgrades keeps their existing stored login (except in the second-application branch; see "Decided").

### Implementation outline

1. **Rename the flow so the name stops lying.** `pkce_flow.go` becomes `device_flow.go` and `PKCEFlow` becomes `DeviceFlow` (constructor, the `TokenManager.Flow` field type, the construction in `cli/cmd/root.go`, the copy in `cli/cmd/login.go`, and the test helpers follow). The token-endpoint client stays on the type: `OAuthConfig`, `DefaultOAuthConfig`, `errInvalidGrant`, `defaultUserAgent`, `RefreshAccessToken`, and `TokenResponse` are unchanged in behavior. One signature change: `postForm(path, data)` becomes `postForm(ctx, path, data)` using `http.NewRequestWithContext` (shared conventions). `RefreshAccessToken` has no context today and `TokenManager.ResolveToken` has none to give, so it passes `context.Background()`, unchanged behavior. Refresh is the one path the rest of the CLI calls, and it must not be duplicated. `randomToken` loses its last caller with the PKCE pair and is deleted too, or the linter flags it. In the second-application branch of Milestone 1, `prodOAuthClientID` changes to the new application's client ID (the constant's comment says which application and when it was created).
2. **Replace `Login`.** Delete the PKCE pair, `state`, the loopback listener, `callbackHandler`, `LoginTimeout` (replaced by the `Sleep` and `Now` fields), and `newPKCEPair`. The new `Login(ctx)`:
   - POSTs the device authorization request through `postForm(ctx, ...)` and parses the response into a struct with `device_code`, `user_code`, `verification_uri`, `verification_uri_complete`, `expires_in`, `interval`. Apply the defaults from the shared conventions. Every error here, including the `errInvalidGrant` sentinel, is wrapped into the grant-setting message from the shared conventions with Clerk's description appended. Do not copy `exchangeCode`'s `errors.Is(err, errInvalidGrant)` mapping into this step: here `invalid_grant` means the grant is disabled, not that a sign-in attempt expired.
   - Prints, in this order: the verification URI, the user code, then attempts `Browser.Open(verification_uri_complete)` (falling back to `verification_uri` if the complete form is empty) and prints "(Could not open browser automatically)" on failure, then "Waiting for authorization...".
   - Polls per the shared conventions: computes the deadline from `Now()` plus `expires_in`, and on each iteration calls `Sleep(ctx, interval)`, then checks `Now()` against the deadline, then POSTs the poll with `ctx`. `postForm` already turns `invalid_grant` into the `errInvalidGrant` sentinel and other OAuth errors into `auth error: <code>` errors; the poll loop needs to see the raw error code to distinguish `authorization_pending` and `slow_down` from terminal errors, so either extend `postForm` to expose the code or give the poll its own request helper that shares the header and context logic. Do not copy the `User-Agent` handling into a second place. After a 200, check `ctx.Err()` before returning tokens (shared conventions).
   - Keeps the two loud checks on success: empty `access_token` fails at login; empty `refresh_token` fails at login with the "is the OAuth app missing the offline_access scope?" wording.
3. **Rewrite the package comment** as a description of the current design, not of what it replaced: the device grant was chosen because the browser can be on any device, which is what makes SSH and container logins work; the grant uses no redirect URI and no PKCE, so the Clerk application's redirect URI and `pkce_required` setting are not exercised by the CLI; the terminal prints the URL and code before opening the browser because that printout is the SSH path and the manual-entry self-check; link phishing (RFC 8628 §5.4) is defended by Clerk's consent page, not by the CLI, and that is an accepted change from the loopback flow; the `User-Agent` is required, not cosmetic; a disabled grant surfaces as `invalid_grant` at the device authorization step, which is why that step has its own error mapping. This rationale must survive in the code.
4. **`cli/cmd/login.go`:** update the `Long` help text (no more "requires a browser on this machine"; say the URL can be opened on any device; `--token` is for CI and scripts). `loginWithOAuth` keeps its shape; only the type name changes.
5. **`cli/cmd/root.go`:** constructor rename. The `User-Agent` with the CLI version stays.
6. **`cli/README.md`, "Clerk OAuth Setup":** rewrite to the current requirements: public application, `device_authorization_grant_enabled` ON (defaults OFF on creation, the same default-off class as the flags the July rewrite hit), instance `oauth_jwt_access_tokens` ON, `offline_access` requested. Say `pkce_required` and the redirect URI are not used by the device grant. Update the "Files to Update" pointer to the renamed file.

## Milestone 4: production rollout and CLI release

### Goal and outcome

The released CLI binary signs in with the device grant against production, and the production Clerk application is configured before any user can download that binary.

- The production "Tiddly CLI" application has the device grant enabled, with `pkce_required` still `true`. In the second-application branch, the production "Tiddly CLI (device)" application exists with the settings Milestone 1 recorded, and the released binary carries its client ID.
- A snapshot build of the new CLI logs in against production end to end before the release is tagged.
- The release is published and `tiddly update` on an older install picks it up.
- Users on the previous binary are not broken at any point in the sequence.

### Implementation outline

Order is load-bearing: the production toggle comes first, because a new binary against an application without the grant fails at the first request. Enabling the grant does not affect the old binary, whose authorization-code flow keeps working.

1. Operator step, show and approve: enable `device_authorization_grant_enabled` on the production "Tiddly CLI" application. Read it back. In the second-application branch, instead create the production "Tiddly CLI (device)" application with the settings recorded in Milestone 1 (a separately approved change), read it back, and confirm the client ID in `DefaultOAuthConfig` matches before building. `pkce_required` is not patched in either branch.
2. Build a snapshot (`make cli-snapshot`) and run `tiddly login` with no OAuth or API overrides, so it targets production, but with `XDG_CONFIG_HOME` set to a temporary directory and `--keyring=file`, so the operator's real login is neither overwritten nor cleared by the `tiddly logout` at the end. Complete the login, confirm `tiddly auth status` shows method `oauth` and the operator's production email, run `tiddly status`, then `tiddly logout`.
3. Merge the branch to `main` (the user merges; the agent does not open or merge pull requests). The docs from Milestone 3 deploy to tiddly.me on merge, so tag the release right after the merge to keep the window where the site describes an unreleased binary to minutes.
4. Tag `cli/v<next minor>` per `cli/README.md` "Releases" and push the tag (the user does this or approves it). Confirm the GitHub release appears with binaries.
5. On a machine with the previous version installed, run `tiddly update` and then `tiddly login` against production.
6. **Follow-up, after old binaries are retired.** The authorization-code flow stays enabled on the "Tiddly CLI" application after this release: Clerk still accepts `/oauth/authorize` for the CLI's public client ID with the loopback redirect, which no binary from this release onward uses. It stays until every CLI user has updated, because updates are manual (`tiddly update` nudges, it does not force). Condition for running the follow-up: confirm with the known CLI users (at beta scale, a short list) that each has updated. Then, as a separately approved production change: in the likely branch (one application), remove the `http://127.0.0.1/callback` redirect URI (if Clerk requires at least one redirect URI on an application, or offers a per-application switch for the authorization-code grant, read Clerk's OAuth application API docs at that point and pick the option that disables the surface); in the second-application branch, delete the old "Tiddly CLI" application outright, which also invalidates any refresh tokens it issued, so any straggler on an old binary is asked to log in again on next use. `pkce_required` is never touched in either branch. Record the result in the `clerk/README.md` per-application table.

- The as-executed section records the production PATCH commands and read-backs, the snapshot login transcript (redacted), the release tag, and the `tiddly update` result.

- Known limitation, recorded in the ledger addendum: the hosted verification page is part of Clerk's Account Portal, so the portal cannot be disabled without breaking CLI login.
- The retired-binaries follow-up (step 6) is recorded in the `clerk/README.md` per-application table with its condition, so the dormant authorization-code surface has a written reason and an exit.
