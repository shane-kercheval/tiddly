# Enable Client ID Metadata Documents for MCP OAuth connectors

**Status**: Planned
**Date**: 2026-10-02
**Scope**: The Clerk authorization server configuration behind both MCP servers (content and prompts), the comments and docs that describe how MCP clients register, and a verification pass against real clients. No MCP server code changes are required. Out of scope: the CLI device-flow login (separate plan), deleting the existing DCR registrations (separate decision, see Known limitations), and any change to the scopes the servers publish.

## Open decisions

- **Client admission mode.** Clerk offers three modes once CIMD is on: "Any compatible CIMD client", "Pre-registered and previously connected clients", and "Pre-registered clients only". Default for this plan: **"Any compatible CIMD client"**, because the product promise is that a user pastes a server URL into any MCP-capable app and signs in, and the other two modes would require an operator to pre-register every client vendor. Confirm before Milestone 2 flips production.

## Decided

- CIMD is enabled on both Clerk instances (dev, then prod). Dynamic Client Registration (DCR) **stays on**, because Antigravity and Cursor have no CIMD support and would otherwise lose OAuth entirely.
- `SCOPES_SUPPORTED` in `backend/src/shared/mcp_oauth.py` keeps `offline_access` even though the 2026-07-28 MCP spec says servers SHOULD NOT publish it. DCR clients derive their registered scopes from that list, and without `offline_access` Clerk issues them no refresh token. The line can go only when DCR is retired. The rationale is recorded in the module comment (Milestone 3), not just here.
- No code path in the MCP servers or the backend changes behavior within this plan. The only code edits are comments and docstrings.
- **Prerequisite, shipped as its own PR before Milestone 1: the API's application logging is configured so INFO lines reach Railway.** `backend/src/core/auth.py` writes `clerk_oauth_token_accepted client_id=... sub=...` with `logger.info`, the security review's observability for accepted OAuth tokens, but the API configures no logging (the only `logging.basicConfig` calls are in the three cron tasks, and `Dockerfile.api` starts uvicorn with no log config), so the `core.auth` logger sits at the default WARNING and the line has never been emitted in any environment. The fix: configure logging in `api/main.py` at INFO for the application's own loggers, leaving uvicorn's loggers alone, with one test that captures the accepted-token line at INFO through the configured logging. A scan of the backend's 22 `logger.info` calls found none that log token, email, key, or secret values; re-check that during the PR. This is a defect fix independent of CIMD, kept out of this plan's milestones so the plan's no-behavior-change promise holds.

## Context: why this change

**What CIMD is.** With Dynamic Client Registration (DCR, RFC 7591), every AI app that connects to a Tiddly MCP server first calls Clerk's `/oauth/register` endpoint and creates a new OAuth application record on our Clerk instance. With Client ID Metadata Documents (CIMD, IETF draft `draft-ietf-oauth-client-id-metadata-document`), the client's ID *is* an HTTPS URL on the vendor's own domain that serves a JSON document listing the client's name and redirect URIs. Clerk fetches that document at authorization time and saves a client record (the ID URL, display name, allowed scopes, admission status, and metadata fetch status, listed on the Dashboard's OAuth applications Applications tab) but issues no credentials. Examples that exist today: Claude's hosted apps use `https://claude.ai/oauth/mcp-oauth-client-metadata`, Claude Code uses `https://claude.ai/oauth/claude-code-client-metadata`, ChatGPT uses `https://chatgpt.com/oauth/client.json`, VS Code uses `https://vscode.dev/oauth/client-metadata.json`.

**The MCP spec deprecated DCR.** Spec revision 2026-07-28 says authorization servers and clients SHOULD support CIMD and MAY support DCR, with the note "Dynamic Client Registration is deprecated and retained for backwards compatibility". The deprecated-features registry lists DCR with earliest removal in the first revision on or after 2027-07-28. Clients that support both use this priority: pre-registered credentials, then CIMD if the authorization server advertises `client_id_metadata_document_supported`, then DCR if it advertises `registration_endpoint`.

**Clerk supports CIMD as a GA feature and recommends it over DCR.** It is an instance-level setting, off by default. Clerk's own MCP guide says to prefer CIMD and enable DCR only for clients that cannot do CIMD.

**Our production instance is on DCR only, and DCR has grown without bound.** On 2026-10-01 the production instance (`clerk.tiddly.me`) advertised `registration_endpoint` and did not advertise `client_id_metadata_document_supported`. It held 2,029 OAuth application records, 2,028 of them dynamically registered. Antigravity created 1,991 of those (1,776 named "Google Antigravity" and 215 named "antigravity-client"), at 5 to 16 per day over the last two weeks, because it re-registers on every connection. All other clients together account for 38. CIMD stops this growth for the clients that support it (Claude, Claude Code, ChatGPT, VS Code). It does not stop Antigravity.

**What a user sees after this change.** Nothing different in the connect flow: paste the URL, sign in, approve. The approval screen for a CIMD client shows the name from the vendor-hosted metadata document rather than a name the client typed into a registration call. Existing connections keep working, because refresh-token renewals never touch the authorize endpoint.

## Conventions for every milestone

- **Production Clerk is a shared system.** Show each `clerk api` write or Dashboard change to the user and wait for approval before making it. Read-only commands (`clerk api` GETs, `curl` of well-known URLs) need no approval.
- **Dev instance first, production second.** Milestone 1 proves the flow on the dev instance. Milestone 2 repeats the proof on production.
- **Record evidence in the verification notes.** Append a dated addendum to `docs/implementation_plans/2026-07-16-mcp-connector-verification-notes.md` with the same table shape the 2026-08-09 addendum uses (client, result, registration observed). That file is the evidence; the user-facing docs are the maintained artifact.
- **The decisive check for "this client used CIMD" is the client ID Clerk saw.** A DCR client presents a Clerk-generated opaque client ID. A CIMD client presents its metadata URL (for example `https://claude.ai/oauth/claude-code-client-metadata`). Three places show it, in order of preference:
  1. The Clerk Dashboard: OAuth applications → Applications tab lists each saved CIMD client with its Client ID URL and creation date. A new row whose creation time matches the connection is proof for any client, including Claude web and ChatGPT, where the agent cannot see the authorize request.
  2. For Claude Code, the authorize URL it prints or opens carries `client_id=https://claude.ai/oauth/claude-code-client-metadata`.
  3. The backend log line `clerk_oauth_token_accepted client_id=...`, available once the logging prerequisite in the Decided section has shipped. On dev, read the local API's stderr; on prod, Railway logs.

  Do not use the `/oauth_applications` record count as proof until Milestone 1 has established whether saved CIMD clients appear in that endpoint (Milestone 1 step 8).
- **Scripted metadata check.** Keep this check and its output with the evidence:

  ```sh
  curl -s https://<frontend-api>/.well-known/oauth-authorization-server \
    | python3 -c "import json,sys; d=json.load(sys.stdin); print('cimd', d.get('client_id_metadata_document_supported')); print('dcr', d.get('registration_endpoint')); print('auth_methods', d.get('token_endpoint_auth_methods_supported'))"
  ```

  Expected after enabling: `cimd True`, `dcr https://<frontend-api>/oauth/register` (DCR still on), and `none` in the auth methods (Claude requires both `client_id_metadata_document_supported: true` and `none` before it chooses CIMD; production already lists `none`). Run it once *before* enabling and confirm it prints `cimd None`, so the check is known to fail on the old state.

## Milestone 1: CIMD works on the dev instance with real clients

### Goal and outcome

Turn CIMD on for the development Clerk instance and prove that CIMD-capable clients connect through it, that DCR-only clients still connect through DCR, and that the backend accepts the resulting tokens. This milestone answers the one open technical question before production is touched.

- Claude Code connects to a locally running MCP server (pointed at the dev Clerk instance) and the token it presents carries the `https://claude.ai/oauth/claude-code-client-metadata` client ID.
- MCP Inspector (a DCR client) still connects, and a new registration record appears for it. This proves CIMD and DCR coexist on one instance.
- The local backend API accepts a CIMD-issued access token: a tool call succeeds end to end.
- The answer to "does Clerk accept Claude Code's loopback redirect when the port differs from the metadata document?" is recorded with evidence, and if Claude Code fell back to DCR, the recorded cause is the one Clerk reported, not the presumed one.
- It is known whether a saved CIMD client appears in the `clerk api /oauth_applications` response and counts toward `total_count`, so Milestone 2 can use the count correctly.
- It is known what happens to a CIMD client's refresh token when CIMD is turned off, so Milestone 2's rollback paragraph states the real cost.

### Implementation outline

1. Run the scripted metadata check against the dev Frontend API and record the pre-change output.
2. Enable "Publish CIMD support" on the dev instance, admission mode "Any compatible CIMD client". The Dashboard path is OAuth applications → Settings → Client onboarding. The API equivalent is `clerk api /instance/oauth_application_settings --instance dev -X PATCH` on the `client_id_metadata_documents_*` fields that the GET already shows (`client_id_metadata_documents_advertised`, `client_id_metadata_documents_only_allow_pre_registered_clients`, `client_id_metadata_documents_block_implicitly_allowed_clients`). The mapping from the three Dashboard admission modes to the two admission booleans is not documented in a page I could verify. Confirm it from the Dashboard (set the mode there and GET the settings) rather than guessing, and record the mapping in `clerk/README.md` in Milestone 3.
3. Re-run the metadata check. `client_id_metadata_document_supported` must now be `true` and `registration_endpoint` must still be present.
4. Start the local API and the content MCP server configured for the dev instance (the existing `CLERK_FRONTEND_API` and `CONTENT_MCP_RESOURCE_URL` env conventions). The precedent is the "Claude Code CLI (localhost + Clerk dev, pre-merge)" row in the verification notes' 2026-08-09 addendum, which ran the full flow with tool calls against a local server.
5. Connect Claude Code with `claude mcp add --transport http` and authenticate. This is the client most likely to fall back to DCR, and there are two distinct causes to tell apart. (a) Redirect mismatch: its metadata document lists portless `http://localhost/callback` and `http://127.0.0.1/callback` but it sends a port at runtime, and Clerk's docs say the requested `redirect_uri` must exactly match an entry. (b) Document fetch failure: Clerk must fetch `https://claude.ai/oauth/claude-code-client-metadata`, and claude.ai's bot protection has returned 403 to some non-browser fetchers; Clerk's docs say a client whose document cannot be fetched shows metadata status "Error" in the Dashboard and its flow cannot complete. Both produce the same symptom (a new DCR registration and an opaque `client_id`). On fallback, capture the authorize redirect's `error` and `error_description` and the Dashboard entry's metadata fetch status, and record the cause Clerk reported. Either outcome is a result, not a failure of this milestone: CIMD still serves the hosted Claude apps and ChatGPT, whose redirects are fixed HTTPS URLs.
6. Connect MCP Inspector with Client ID, Secret, and Scope empty (its DCR path) and confirm it still works.
7. Make one real tool call from each client and confirm the client ID by the checks in the Conventions section: the Dashboard's Applications tab shows the Claude Code metadata URL as a saved CIMD client, and the log line (if the logging prerequisite has shipped) shows the metadata URL for Claude Code and an opaque ID for Inspector.
8. Establish how CIMD clients surface in the API. Run `clerk api "/oauth_applications?limit=100" --instance dev` and compare with the Dashboard's Applications tab. Record whether the saved CIMD client appears in the API response and in `total_count`, and if it does, which fields distinguish it from a DCR registration (a URL-shaped `client_id`, the `dynamically_registered` value). Milestone 2's count check is written from this answer.
9. Append the addendum to the verification notes.
10. **Last, the rollback drill.** It must be the final step because it ends Claude Code's connection. With Claude Code connected via CIMD, turn CIMD off on the dev instance (same toggle). Then force a refresh: Claude Code stores its MCP OAuth tokens locally, so replay its current refresh token with one `curl` to `/oauth/token` using `grant_type=refresh_token`, the metadata URL as `client_id`, and an explicit `User-Agent` (Clerk 403s default agents). Record whether Clerk returns a new token pair or an error, and the error body. Clerk rotates refresh tokens and treats a replay of a rotated-out token as theft, revoking the whole grant (ledger question 2, observed 2026-07-13), so after this `curl` Claude Code's stored token is stale and its next refresh will fail. That failure is the expected consequence of the drill, not a CIMD bug. If the stored token cannot be read, leave CIMD off on dev for 24 hours instead and retry a tool call. Turn CIMD back on, then re-authenticate Claude Code.

Do not change `clerk/config.dev.json`: `clerk config pull` does not include `oauth_application_settings` (see `clerk/README.md`), so the committed file has nothing to pick up. The settings table in that README is the record, updated in Milestone 3.

### Definition of done

- Verification notes addendum with: the before and after metadata-check output; one row per client (Claude Code, MCP Inspector) with the observed `client_id`, where it was observed (Dashboard, authorize URL, log), and whether a DCR registration was created; on a Claude Code fallback, Clerk's reported error and the Dashboard metadata fetch status; the API-versus-Dashboard answer from step 8; and the rollback drill's token-endpoint response.
- The backend accepted a CIMD-issued token with no code change. If anything in `decode_clerk_jwt` rejected a URL-shaped `client_id`, stop and report rather than patching: the policy in that function was a security-review decision and must be changed deliberately.
- No automated tests are added in this milestone. The behavior under test lives in Clerk, and the existing tests in `backend/tests/shared/test_mcp_oauth.py`, `backend/tests/prompt_mcp_server/test_oauth_discovery.py`, and `backend/tests/security/test_mcp_oauth_surface.py` already pin the protected-resource metadata, which does not change.

## Milestone 2: CIMD is on in production and verified with every client

### Goal and outcome

Flip the production instance and re-verify the clients users actually connect from.

- A fresh connection from Claude (web) uses CIMD: the Dashboard's Applications tab gains a saved CIMD client with ID `https://claude.ai/oauth/mcp-oauth-client-metadata`, no DCR registration appears, and the production log (with the logging prerequisite shipped) shows that URL as the `client_id`.
- A fresh connection from Claude Code uses CIMD if Milestone 1 showed Clerk accepts its loopback redirect, otherwise DCR, matching the Milestone 1 result.
- A fresh connection from ChatGPT uses CIMD with client ID `https://chatgpt.com/oauth/client.json` (production advertises `authorization_response_iss_parameter_supported: true`, so ChatGPT should use its stable document rather than a per-callback one; record which it used).
- Existing connections (every connector that was working the day before) still work without re-authenticating.
- Antigravity still connects, through DCR, and its registration count keeps growing at the prior rate. Nothing regresses for it.

### Implementation outline

1. Run the scripted metadata check against `https://clerk.tiddly.me` and record the output.
2. Record the production registration count with `clerk api "/oauth_applications?limit=1" --instance prod` (`total_count`) so the "no new registrations for CIMD clients" check has a baseline.
3. Show the user the exact production change (Dashboard toggle plus admission mode, or the `clerk api` PATCH with the field mapping confirmed in Milestone 1) and wait for approval.
4. Enable, re-run the metadata check, and confirm DCR is still advertised.
5. Before connecting anything new, exercise an existing connection (for example, a tool call from the already-connected Claude web connector) to confirm it still works.
6. Connect fresh from each client in the outcome list, following the per-app steps in `frontend/src/content/prose/connect-ai-apps.md`. For "fresh", remove the existing connection in the app first, as the July notes did. Make one real tool call per client.
7. Confirm each client's ID by the Conventions checks (Dashboard Applications tab first, Railway log line second), and re-read `total_count`. Interpret the count with Milestone 1 step 8's answer: if saved CIMD clients do not appear in `/oauth_applications`, the count must rise only by the DCR connections you made plus Antigravity's background rate; if they do appear, the count must rise by those plus one per new CIMD client, each identifiable by its URL-shaped `client_id`.
8. Run the deployed security suite (`backend/tests/security/deployed/test_live_penetration.py`) as a regression check on the auth surface. `AGENTS.md` asks for this after any auth change, and this is one even though no code changed.
9. Append the production addendum to the verification notes.

Rollback is the same toggle turned off. A CIMD client that can no longer authorize falls back to DCR on its next fresh connection, because DCR stays advertised. What happens to a CIMD client's existing refresh token is whatever Milestone 1's rollback drill observed; write that result here before flipping production. If the drill showed refresh fails, state the rollback cost plainly: every connection made via CIMD since the flip must re-authenticate, while DCR connections (Antigravity, pre-flip connectors) are unaffected.

### Definition of done

- Verification notes addendum with the client table, the before and after `total_count`, and the metadata-check outputs.
- The deployed security suite passed, with its output kept alongside the evidence.
- Any client that did not use CIMD is listed by name with the observed reason.

## Known limitations

- **Antigravity and Cursor stay on DCR**, so registration records keep accumulating at Antigravity's rate (about 300 a month at the current pace). Deleting old registrations is a separate decision because deleting a record revokes the refresh tokens of any live connection that still uses it. The conservative option, deleting only Antigravity-named records older than 30 days after confirming with the affected user that re-authenticating is acceptable, is noted here and not scheduled.
- **`offline_access` remains in `scopes_supported`** against the spec's SHOULD NOT, for the reason recorded in the module comment. Revisit when DCR is turned off.
- **Claude Code under CIMD is unverified until Milestone 1.** Two things could make it fall back to DCR: Clerk rejecting the runtime loopback port against the portless redirect in its metadata document, or Clerk failing to fetch the document from claude.ai. The fallback is automatic either way. Record the observed cause in this section when known, and do not generalize a fetch failure into a loopback-client limitation.
- **The rollback cost for CIMD-connected clients is unknown until Milestone 1's drill.** Clerk's docs do not say whether a CIMD client's refresh token keeps working after CIMD is turned off. Milestone 2's rollback paragraph is written from the drill result.
- **The spec's `scope` parameter in the `WWW-Authenticate` challenge (SHOULD) is not implemented.** It was not part of this discussion. It is a small server change if wanted later.
- **Antigravity setup instructions do not exist in the user docs.** This plan only removes the false claim that Antigravity lacks OAuth support.
