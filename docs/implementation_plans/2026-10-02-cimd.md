# Enable Client ID Metadata Documents for MCP OAuth connectors

**Status**: Planned
**Date**: 2026-10-02
**Scope**: The Clerk authorization server configuration behind both MCP servers (content and prompts), the comments and docs that describe how MCP clients register, and a verification pass against real clients. No MCP server code changes are required. Out of scope: the CLI device-grant login (its own plan, `docs/implementation_plans/2026-10-02-device-code.md` on the `device-code` branch, not yet on `main`), deleting the existing DCR registrations (separate decision, see Known limitations), and any change to the scopes the servers publish.

## Open decisions

- **Client admission mode.** Clerk offers three modes once CIMD is on: "Any compatible CIMD client", "Pre-registered and previously connected clients", and "Pre-registered clients only". Default for this plan: **"Any compatible CIMD client"**, because the product promise is that a user pastes a server URL into any MCP-capable app and signs in, and the other two modes would require an operator to pre-register every client vendor. Confirm before Milestone 2 flips production.

## Decided

- CIMD is enabled on both Clerk instances (dev, then prod). Dynamic Client Registration (DCR) **stays on**, because Antigravity, the largest source of registrations, has no CIMD support and would otherwise lose OAuth entirely, as would any other OAuth client without CIMD support.
- **A Claude Code failure on dev is decided when it is observed, with the operator.** Milestone 1 runs with the operator present (the browser sign-ins need them), so if step 5's "failed connection" outcome happens, stop, report what Clerk returned, and decide together whether and how to proceed. Production cannot change without the operator's approval anyway (see Conventions).
- **Cursor is out of scope.** It is not a Tiddly-supported client: it appears nowhere in `frontend/src/content/prose/connect-ai-apps.md`, the CLI's tool list, or the agent-facing `llms*.txt` files, and it entered an earlier draft of this plan from web research. Docs written by this plan do not mention it.
- **Antigravity is checked passively in Milestone 2.** The operator's own Antigravity connects to both MCP servers with Personal Access Tokens (checked 2026-10-11: both Tiddly entries in `~/.gemini/config/mcp_config.json` set an `Authorization` header), so it never runs the OAuth flow and is not the source of the 1,991 registrations. Those come from other users connecting Antigravity through OAuth, so the check is that the registration count keeps rising at the prior rate.
- `SCOPES_SUPPORTED` in `backend/src/shared/mcp_oauth.py` keeps `offline_access` even though the 2026-07-28 MCP spec says servers SHOULD NOT publish it. DCR clients derive their registered scopes from that list, and without `offline_access` Clerk issues them no refresh token. The line can go only when DCR is retired. The rationale is recorded in the module comment (Milestone 3), not just here.
- No code path in the MCP servers or the backend changes behavior within this plan. The only code edits are comments and docstrings.
- **Prerequisite, shipped as its own PR before Milestone 1: the API's application logging is configured so INFO lines reach Railway.** `backend/src/core/auth.py` writes `clerk_oauth_token_accepted client_id=... sub=...` with `logger.info`, the security review's observability for accepted OAuth tokens, but the API configures no logging (the only `logging.basicConfig` calls are in the three cron tasks, and `Dockerfile.api` starts uvicorn with no log config), so the `core.auth` logger sits at the default WARNING and the line has never been emitted in any environment. The fix, specified here because the two obvious implementations differ in what they leak:
  - **Enumerate the first-party loggers; leave the root logger alone.** `PYTHONPATH` is `backend/src`, so the application has no single root package: its loggers are `api`, `core`, `services`, `shared`, `db`, `models`, and `schemas`. The setup in `api/main.py` attaches a stderr handler and INFO level to exactly those names and does not touch the root logger or uvicorn's loggers. Do not use the cron tasks' `logging.basicConfig(level=INFO)` pattern: it sets the root logger to INFO, which makes `httpx` (used by `services/url_scraper.py`, `services/llm_service.py`, and both MCP `api_client.py` modules) emit one `HTTP Request: <method> <url>` line per outbound call, putting every user-submitted scrape URL and every LLM provider call into Railway logs, and makes `sqlalchemy.engine` emit every SQL statement (its effective level becomes INFO even with `echo=False`). The plan's scan of our own `logger.info` calls would not catch either, because neither is our call. A comment on the enumerated list states that it exists to keep `httpx` and `sqlalchemy.engine` quiet. `mcp_server` and `prompt_mcp_server` are absent on purpose: they are separate processes, and their logging is out of scope for the API's setup.
  - **The accepted-token line fires once per OAuth-authenticated API request**, because `decode_clerk_jwt` runs in `_authenticate_user` before `get_or_create_user` consults the auth cache. One MCP tool call therefore produces at least one INFO line. This is intended at beta scale; revisit if volume becomes a problem.
  - **Tests.** One test that captures the accepted-token line at INFO through the configured logging, minting its token with `client_id="https://claude.ai/oauth/claude-code-client-metadata"` and asserting both acceptance and the logged value. This pins the "URL-shaped client IDs are accepted, no allowlist" decision in `decode_clerk_jwt`, which the existing tests in `backend/tests/core/test_auth_clerk.py` do not (they mint only the opaque `zTESTclientid123`). One test asserting `logging.getLogger("httpx").getEffectiveLevel()` and `logging.getLogger("sqlalchemy.engine").getEffectiveLevel()` are both WARNING after the setup runs.
  - A scan of the backend's `logger.info` calls found none that log token, email, key, or secret values; re-check that during the PR.

  This is a defect fix independent of CIMD, kept out of this plan's milestones so the plan's no-behavior-change promise holds.

## Context: why this change

**What CIMD is.** With Dynamic Client Registration (DCR, RFC 7591), every AI app that connects to a Tiddly MCP server first calls Clerk's `/oauth/register` endpoint and creates a new OAuth application record on our Clerk instance. With Client ID Metadata Documents (CIMD, IETF draft `draft-ietf-oauth-client-id-metadata-document`), the client's ID *is* an HTTPS URL on the vendor's own domain that serves a JSON document listing the client's name and redirect URIs. Clerk fetches that document at authorization time and saves a client record (the ID URL, display name, allowed scopes, admission status, and metadata fetch status, listed on the Dashboard's OAuth applications Applications tab) but issues no credentials. Examples that exist today: Claude's hosted apps use `https://claude.ai/oauth/mcp-oauth-client-metadata`, Claude Code uses `https://claude.ai/oauth/claude-code-client-metadata`, ChatGPT uses `https://chatgpt.com/oauth/client.json`, VS Code uses `https://vscode.dev/oauth/client-metadata.json`.

**The MCP spec deprecated DCR.** Spec revision 2026-07-28 says authorization servers and clients SHOULD support CIMD and MAY support DCR, with the note "Dynamic Client Registration is deprecated and retained for backwards compatibility". The deprecated-features registry lists DCR with earliest removal in the first revision on or after 2027-07-28. Clients that support both use this priority: pre-registered credentials, then CIMD if the authorization server advertises `client_id_metadata_document_supported`, then DCR if it advertises `registration_endpoint`. That is a *selection* order based on what the server advertises. Neither the spec nor the Claude Code docs say a client retries through DCR after the authorization server rejects its CIMD attempt, so this plan does not assume it does (see Milestone 1 step 5).

**Clerk supports CIMD as a GA feature and recommends it over DCR.** It is an instance-level setting, off by default. Clerk's own MCP guide says to prefer CIMD and enable DCR only for clients that cannot do CIMD.

**Our production instance is on DCR only, and DCR has grown without bound.** On 2026-10-01 the production instance (`clerk.tiddly.me`) advertised `registration_endpoint` and did not advertise `client_id_metadata_document_supported`. It held 2,029 OAuth application records, 2,028 of them dynamically registered. Antigravity created 1,991 of those (1,776 named "Google Antigravity" and 215 named "antigravity-client"), at 5 to 16 per day over the last two weeks, because it re-registers on every connection. All other clients together account for 38. CIMD stops this growth for the clients that support it (Claude, Claude Code, ChatGPT, VS Code). It does not stop Antigravity.

**What a user sees after this change.** Nothing different in the connect flow: paste the URL, sign in, approve. The approval screen for a CIMD client shows the name from the vendor-hosted metadata document rather than a name the client typed into a registration call. Existing connections keep working, because refresh-token renewals never touch the authorize endpoint.

## Conventions for every milestone

- **Production Clerk is a shared system.** Show each `clerk api` write or Dashboard change to the user and wait for approval before making it. Read-only commands (`clerk api` GETs, `curl` of well-known URLs) need no approval.
- **Dev instance first, production second.** Milestone 1 proves the flow on the dev instance. Milestone 2 repeats the proof on production.
- **Tokens never appear in commands, output, or notes.** The rollback drill and any manual token-endpoint call go through a short script that reads the stored token from wherever the client keeps it, posts it, and prints only the HTTP status, presence booleans for `access_token` and `refresh_token`, `expires_in`, `scope`, and the OAuth `error` and `error_description`. No token value goes into a shell argument (visible in process lists and shell history), stdout, or the verification notes. When a step needs a token's claims (the `scope` claim, `client_id`), decode the payload and print only those claims.
- **Record evidence in the verification notes.** Append a dated addendum to `docs/implementation_plans/2026-07-16-mcp-connector-verification-notes.md` with the same table shape the 2026-08-09 addendum uses (client, result, registration observed). That file is the evidence; the user-facing docs are the maintained artifact.
- **The decisive check for "this client used CIMD" is the client ID Clerk saw.** A DCR client presents a Clerk-generated opaque client ID. A CIMD client presents its metadata URL (for example `https://claude.ai/oauth/claude-code-client-metadata`). Three places show it, in order of preference:
  1. The Clerk Dashboard: OAuth applications → Applications tab lists each saved CIMD client with its Client ID URL and creation date. A new row whose creation time matches the connection is proof for any client, including Claude web and ChatGPT, where the agent cannot see the authorize request.
  2. For Claude Code, the authorize URL it prints or opens carries `client_id=https://claude.ai/oauth/claude-code-client-metadata`.
  3. The backend log line `clerk_oauth_token_accepted client_id=...`, available once the logging prerequisite in the Decided section has shipped. On dev, read the local API's stderr; on prod, Railway logs.

  Do not use the `/oauth_applications` record count as proof until Milestone 1 has established whether saved CIMD clients appear in that endpoint (Milestone 1 step 9).
- **Scripted metadata check.** Keep this check and its output with the evidence:

  ```sh
  curl -s https://<frontend-api>/.well-known/oauth-authorization-server \
    | python3 -c "import json,sys; d=json.load(sys.stdin); print('cimd', d.get('client_id_metadata_document_supported')); print('dcr', d.get('registration_endpoint')); print('auth_methods', d.get('token_endpoint_auth_methods_supported'))"
  ```

  Expected after enabling: `cimd True`, `dcr https://<frontend-api>/oauth/register` (DCR still on), and `none` in the auth methods (Claude requires both `client_id_metadata_document_supported: true` and `none` before it chooses CIMD; production already lists `none`). Run it once *before* enabling and confirm it prints `cimd None`, so the check is known to fail on the old state.

## Milestone 1: CIMD works on the dev instance with real clients

### Goal and outcome

Turn CIMD on for the development Clerk instance and prove that CIMD-capable clients connect through it, that DCR-only clients still connect through DCR, and that the backend accepts the resulting tokens. This milestone answers the open technical questions before production is touched. **At least one CIMD success is required**: the saved-client check, the token-acceptance check, the scope observations, and the rollback drill all need a client that actually authorized through CIMD, so the milestone cannot complete on fallbacks alone.

- Claude Code connects to a locally running MCP server (pointed at the dev Clerk instance) with one of three recorded outcomes: CIMD success (the token carries the `https://claude.ai/oauth/claude-code-client-metadata` client ID), observed DCR fallback (a new registration and an opaque client ID, with the error Clerk reported on the CIMD attempt), or failed connection (no registration, no token). On the third outcome, stop and decide with the operator (see Decided).
- If Claude Code did not succeed through CIMD, a second CIMD-capable client did (VS Code first, Claude web through a tunnel second; step 6).
- MCP Inspector (a DCR client) still connects, and a new registration record appears for it. This proves CIMD and DCR coexist on one instance.
- The local backend API accepts a CIMD-issued access token: a tool call succeeds end to end.
- The answer to "does Clerk accept Claude Code's loopback redirect when the port differs from the metadata document?" is recorded with evidence, and if Claude Code fell back to DCR, the recorded cause is the one Clerk reported, not the presumed one.
- The scopes a CIMD client requests and receives are recorded: the authorize request's `scope`, the access token's `scope` claim, whether a refresh token was issued, and the saved client's allowed scopes in the Dashboard. Milestone 3 writes the `SCOPES_SUPPORTED` comment from these observations, not from Clerk's docs.
- It is known whether a saved CIMD client appears in the `clerk api /oauth_applications` response and counts toward `total_count`, so Milestone 2 can use the count correctly.
- It is known what happens to a CIMD client's refresh token when CIMD is turned off, from a drill with a working baseline, so Milestone 2's rollback paragraph states the real cost.

### Implementation outline

1. Run the scripted metadata check against the dev Frontend API and record the pre-change output.
2. Enable "Publish CIMD support" on the dev instance, admission mode "Any compatible CIMD client". The Dashboard path is OAuth applications → Settings → Client onboarding. The API equivalent is `clerk api /instance/oauth_application_settings --instance dev -X PATCH` on the `client_id_metadata_documents_*` fields that the GET already shows (`client_id_metadata_documents_advertised`, `client_id_metadata_documents_only_allow_pre_registered_clients`, `client_id_metadata_documents_block_implicitly_allowed_clients`). The mapping from the three Dashboard admission modes to the two admission booleans is not documented in a page I could verify. Confirm it from the Dashboard (set the mode there and GET the settings) rather than guessing, and record the mapping in `clerk/README.md` in Milestone 3.
3. Re-run the metadata check. `client_id_metadata_document_supported` must now be `true` and `registration_endpoint` must still be present.
4. Start the local API and the content MCP server configured for the dev instance (the existing `CLERK_FRONTEND_API` and `CONTENT_MCP_RESOURCE_URL` env conventions). The precedent is the "Claude Code CLI (localhost + Clerk dev, pre-merge)" row in the verification notes' 2026-08-09 addendum, which ran the full flow with tool calls against a local server.
5. Connect Claude Code with `claude mcp add --transport http` and authenticate. Expect success: ledger question 2 (observed 2026-07-13) records Clerk matching the CLI app's portless `http://127.0.0.1/callback` redirect against ephemeral loopback ports per RFC 8252, so port-agnostic loopback matching exists for pre-registered apps, and the open question is only whether the CIMD path applies the same rule. Record which of three outcomes happened:
   - **CIMD success.** The authorize URL carries `client_id=https://claude.ai/oauth/claude-code-client-metadata` and the Dashboard's Applications tab gains that client.
   - **Observed DCR fallback.** A new DCR registration and an opaque `client_id`. Two causes produce this symptom and must be told apart. (a) Redirect mismatch: the metadata document lists portless `http://localhost/callback` and `http://127.0.0.1/callback` but Claude Code sends a port at runtime, and Clerk's docs say the requested `redirect_uri` must exactly match an entry. (b) Document fetch failure: Clerk must fetch `https://claude.ai/oauth/claude-code-client-metadata`, claude.ai's bot protection has returned 403 to some non-browser fetchers, and Clerk's docs say a client whose document cannot be fetched shows metadata status "Error" in the Dashboard. Given the ledger evidence, (b) is the more likely cause. Capture the authorize redirect's `error` and `error_description` and the Dashboard entry's metadata fetch status, and record the cause Clerk reported, not the presumed one.
   - **Failed connection.** Clerk rejected the CIMD attempt and Claude Code did not retry through DCR: no new registration, no token, the `/mcp` command shows the server unauthenticated. Capture the same error fields. Nothing in the spec or Claude Code's docs promises a retry, and this observation would prove there is none. Stop and report to the operator before continuing to step 6; whether and how to proceed (for example, Claude Code's `--client-id` pre-registration option) is decided then (see Decided).
6. **If Claude Code did not succeed through CIMD**, obtain the required CIMD success from another client, cheapest first. (i) **VS Code**: its MCP client uses `https://vscode.dev/oauth/client-metadata.json` and reaches a localhost server with no tunnel. Add the local content MCP server URL as an HTTP MCP server in VS Code and authenticate. Record the outcome in the same three-way form; if it also falls back for a loopback reason, that is itself evidence about Clerk's CIMD redirect matching. VS Code's CIMD behavior has not been observed in this repo, so treat it as "try first", not "known to work". (ii) **Claude web through a tunnel**: run `cloudflared` (the per-session tunnel pattern `README_DEPLOY.md` step 6f already uses for webhook testing) to the local content MCP server, set `CONTENT_MCP_RESOURCE_URL` to the tunnel's `https://…/mcp` URL and restart the server, then add the tunnel URL as a custom connector in Claude web. Its redirect is a fixed HTTPS URL on claude.ai, so the loopback question does not apply. Tear the tunnel down and restore `CONTENT_MCP_RESOURCE_URL` afterward.
7. Connect MCP Inspector with Client ID, Secret, and Scope empty (its DCR path) and confirm it still works.
8. Make one real tool call from each client and confirm the client ID by the checks in the Conventions section: the Dashboard's Applications tab shows the CIMD client's metadata URL as a saved client, and the log line (if the logging prerequisite has shipped) shows the metadata URL for the CIMD client and an opaque ID for Inspector. For the CIMD client, also record its scopes, because Milestone 3 writes the `SCOPES_SUPPORTED` comment from this and nothing else verifies the claim: the authorize URL's `scope=` parameter; the access token's `scope` claim (decode the payload and print only that claim, per the Conventions); whether the token response included a refresh token (the drill in step 11 needs one anyway); and the saved client's allowed scopes as shown in the Dashboard. The question these answer is whether Clerk grants `offline_access` to a CIMD client that requests it from our published list, adds it on its own, or neither.
9. Establish how CIMD clients surface in the API. Run `clerk api "/oauth_applications?limit=100" --instance dev` and compare with the Dashboard's Applications tab. Record whether the saved CIMD client appears in the API response and in `total_count`, and if it does, which fields distinguish it from a DCR registration (a URL-shaped `client_id`, the `dynamically_registered` value). Milestone 2's count check is written from this answer.
10. Append the addendum to the verification notes.
11. **Last, the rollback drill.** It must be the final step because it ends the CIMD client's connection. It has a baseline replay so that an error on the real replay can be attributed to CIMD being off rather than to a malformed request (Clerk's token endpoint returns a bare 403 for default User-Agents, and a hand-built public-client refresh can fail on other details). The steps, using Claude Code as the CIMD client (substitute the step 6 client if Claude Code fell back):
    1. **Quit Claude Code** so it cannot rotate the token underneath the drill.
    2. **Read the stored refresh token** through the filtered script described in the Conventions. Claude Code stores its MCP OAuth tokens in the OS credential store; on macOS that is the Keychain, not a file. Verify the location on the machine rather than assuming it. If the token cannot be read, skip to the fallback at the end.
    3. **Baseline replay, CIMD still on.** POST to `/oauth/token` with `grant_type=refresh_token`, the metadata URL as `client_id`, and an explicit `User-Agent`. Expect a new token pair. This proves the request shape. Record the filtered response.
    4. **Prove the new access token works**: one `curl` tool call to the local MCP server with it (the script prints only the HTTP status and whether the response was a valid MCP result).
    5. **Turn CIMD off** on the dev instance (same toggle).
    6. **Real replay** with the *new* refresh token from step 3. Record the filtered response. This is the observation Milestone 2's rollback paragraph is written from.
    7. **Turn CIMD back on**, then re-authenticate Claude Code. Its stored token was rotated out by step 3; Clerk treats a replay of a rotated-out token as theft and revokes the whole grant (ledger question 2, observed 2026-07-13), so its next refresh would have failed anyway. That failure is the expected consequence of the drill, not a CIMD bug.

    Fallback if the stored token cannot be read: leave CIMD off on dev for more than 24 hours (the access-token lifetime), then retry a tool call from Claude Code and record whether its own refresh succeeded. This has no baseline, so a failure is weaker evidence; say so in the notes.

Do not change `clerk/config.dev.json`: `clerk config pull` does not include `oauth_application_settings` (see `clerk/README.md`), so the committed file has nothing to pick up. The settings table in that README is the record, updated in Milestone 3.

### Definition of done

- Verification notes addendum with: the before and after metadata-check output; one row per client (Claude Code, MCP Inspector, and any step 6 client) with the observed `client_id`, where it was observed (Dashboard, authorize URL, log), and whether a DCR registration was created; Claude Code's outcome named as one of the three in step 5, with Clerk's reported error and the Dashboard metadata fetch status on anything other than success; the CIMD client's scope observations from step 8; the API-versus-Dashboard answer from step 9; and the drill's filtered responses (baseline and real), never raw token-endpoint bodies.
- At least one client authorized through CIMD. If none did, the milestone is not done and production is not flipped.
- The backend accepted a CIMD-issued token with no code change. If anything in `decode_clerk_jwt` rejected a URL-shaped `client_id`, stop and report rather than patching: the policy in that function was a security-review decision and must be changed deliberately.
- No automated tests are added in this milestone. The behavior under test lives in Clerk, and the existing tests in `backend/tests/shared/test_mcp_oauth.py`, `backend/tests/prompt_mcp_server/test_oauth_discovery.py`, and `backend/tests/security/test_mcp_oauth_surface.py` already pin the protected-resource metadata, which does not change.

If the drill showed refresh fails, state the rollback cost plainly: every connection made via CIMD since the flip must re-authenticate, while DCR connections (Antigravity, pre-flip connectors) are unaffected.

## Known limitations

- **Antigravity stays on DCR**, so registration records keep accumulating at Antigravity's rate (about 300 a month at the current pace). Deleting old registrations is a separate decision because deleting a record revokes the refresh tokens of any live connection that still uses it. The conservative option, deleting only Antigravity-named records older than 30 days after confirming with the affected user that re-authenticating is acceptable, is noted here and not scheduled.
- **`offline_access` remains in `scopes_supported`** against the spec's SHOULD NOT, for the reason recorded in the module comment. Revisit when DCR is turned off.
- **Claude Code under CIMD is unverified until Milestone 1.** Two things could make Clerk reject its CIMD attempt: the runtime loopback port not matching the portless redirect in its metadata document (unlikely, given the ledger's RFC 8252 observation for pre-registered apps), or Clerk failing to fetch the document from claude.ai. What Claude Code does after a rejection is also unknown: it may fall back to DCR, or it may simply fail. Nothing in the spec or its docs promises a retry. Milestone 1 step 5 records which of the three outcomes happened and the cause Clerk reported; a failed connection is reported to the operator and decided then (see Decided). Do not generalize a fetch failure into a loopback-client limitation.
- **The rollback cost for CIMD-connected clients is unknown until Milestone 1's drill.** Clerk's docs do not say whether a CIMD client's refresh token keeps working after CIMD is turned off. Milestone 2's rollback paragraph is written from the drill result.
- **The consent screen stays forced with CIMD on, so retiring DCR later is not the one-toggle change it looks like.** Enabling DCR force-enabled Clerk's consent screen on every OAuth flow on the instance, including the CLI login (ledger, "As-executed observations", 2026-07-16). Clerk's CIMD docs say CIMD clients always see the consent screen as well. So turning DCR off later would not remove consent for connectors, and whether it removes it for the CLI's pre-registered app is unknown. A future "retire DCR" change must check that, and must also revisit `offline_access` in `scopes_supported` (above) and the pre-deploy DCR registrations that live connections still use.
- **The spec's `scope` parameter in the `WWW-Authenticate` challenge (SHOULD) is not implemented.** It was not part of this discussion. It is a small server change if wanted later.
- **Antigravity setup instructions do not exist in the user docs.** This plan only removes the false claim that Antigravity lacks OAuth support.
