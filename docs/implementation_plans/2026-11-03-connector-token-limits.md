# Limit what an AI app's OAuth token can do in the API

**Status**: Planned
**Date**: 2026-11-03
**Scope**: The backend API's handling of Clerk OAuth access tokens issued to MCP connectors (Claude web, desktop, mobile, Claude Code, Codex, ChatGPT, and any other app a user approves). One new API setting, one Railway variable on the api service, tests, and the docs that describe what a connected app can do. No MCP server behavior change, no CLI change, no Clerk configuration change, no change for session tokens (web app, Chrome extension, iOS) or Personal Access Tokens (PATs).

## Open decisions

None.

## Decided

Who decided each item is marked. Items decided by Shane or the orchestrator are not changed by this plan; new evidence against them is reported in the final report, not acted on.

- **Shane:** fix this by limiting connector tokens in the API.
- **Shane (2026-11-03): allowlist, not blocklist.** A connector token may call only the backend routes the two MCP servers call today (28 route templates, listed in Milestone 2). Every other route returns 403 to a connector token, including any route added later, until someone adds it to the list. The alternative was a blocklist of deletes, `/tokens/*`, `/settings/*`, `/ai/*`, and `/bookmarks/fetch-metadata`. The allowlist won because the dangerous surface is wider than "delete": `POST /bookmarks/{bookmark_id}/share` publishes an item at a public URL, `POST /history/.../restore/{version}` rewrites content, and `GET /users/me` returns the account's email, and a blocklist author has to remember each one. The allowlist's cost is that a new MCP tool that calls a new route needs an allowlist entry, and the drift test in Milestone 2 makes that failure loud rather than silent.
- **Shane (2026-11-03): `content_history.auth_type` keeps the value `session` for connector edits, with no new persisted value.** The column is an audit vocabulary (`session`, `pat`, `dev`, and historical `auth0`) returned by the history API and typed in the frontend, and the `source` column already records `mcp-content` or `mcp-prompt` for MCP traffic. The verified client ID goes into the request context and the log line instead. (If this is ever revisited: the column is `String(10)`, so `connector` fits without a migration, and the only readers are `HistoryResponse.auth_type` and `frontend/src/types.ts`, which treat it as a string.)
- **Shane (2026-11-03): no backward compatibility for direct REST calls made with a connector token.** That use was never documented (the REST docs say PAT), and the MCP tools, the documented path, keep working. Three published statements become false and are rewritten in Milestone 2: `frontend/public/llms-integration.txt` says approving the consent screen "grants that app the same content access as the user's session (there are no granular scopes)"; the OpenAPI description in `backend/src/api/main.py` says "Every authenticated endpoint accepts a bearer token (an IdP session/OAuth JWT, or a `bm_` Personal Access Token)"; the AI note in `frontend/src/content/prose/api.md` says the `/ai/*` endpoints are session-only and PATs get 403, without mentioning connector tokens.
- **Shane (2026-11-03): a connector token may archive items, unarchive bookmarks and notes, and replace an item's links through the edit routes' body fields; the docs say so rather than the code blocking it.** Both plan reviewers found that the three edit routes on the allowlist (`PATCH /bookmarks/{bookmark_id}`, `PATCH /notes/{note_id}`, `PATCH /prompts/name/{name}`) accept two body fields the MCP tools never send: `archived_at` (a past time archives the item; `null` unarchives it) and `relationships` (the list replaces the item's links; `[]` removes them all). Verified in code 2026-11-03: the update schemas declare both fields, the bookmark and note update services load archived items and apply every field in the body, and the relationship sync deletes links absent from the desired set. Unarchiving has one exception: `PATCH /prompts/name/{name}` looks the prompt up with the active-only `get_by_name` (`api/routers/prompts.py`, `services/prompt_service.py`), so an archived prompt returns 404 and is unarchived in the web app. Allowed because both effects are reversible within limits (unarchive in the web app; links return when an earlier version is restored, as long as that version's history row has not aged out under the retention rule in Known limitations) and the plan already accepts that a connector token can overwrite content. The alternative, rejecting the two fields from connector tokens in the three handlers, was not taken. The published promise is: a connected app can read, create, edit, archive, link, and unlink items, but can't delete items, publish to a public link, restore versions, create keys, change settings, or use AI features.

## Context: why this change

**What a connector token is.** When a user connects an AI app to a Tiddly MCP server, Clerk issues that app an OAuth access token: an RFC 9068 JWT with header `typ: at+jwt`, a 24-hour life, a `sub` naming the user, and a `client_id` naming the app. For a CIMD client the `client_id` is the vendor's metadata URL (Claude Code's is `https://claude.ai/oauth/claude-code-client-metadata`); for a DCR client it is a Clerk-generated ID. The `tiddly` CLI's token has the same shape, with the `client_id` of the pre-registered "Tiddly CLI" OAuth application. The MCP servers forward the token unchanged to the backend, which verifies it (`core/auth.py`, `decode_clerk_jwt`).

**The problem.** The backend accepts a connector token on every user-authenticated route, including the routes marked "session-only" (`/tokens/*`, `/settings/*`, `/ai/*`, `/bookmarks/fetch-metadata`), because the M4 decision in the [Clerk migration plan](2026-07-02-clerk-migration.md) made every Clerk OAuth token count as session auth so the CLI could create PATs. The MCP servers deliberately offer no delete tool, but anyone holding a connector token can skip the MCP server and call the REST API. **Verified by running (2026-11-03, mapper agent):** a connector-shaped token signed with the test key from `backend/tests/core/test_auth_clerk.py`, sent through the real FastAPI app and a real Postgres with dev mode off, got 204 on `DELETE /bookmarks/{id}?permanent=true` (the row was gone) and 201 on `POST /tokens/` (a PAT with no expiry was stored). A token signed with the wrong key got 401, so signature verification was active. The holder could be the vendor, an attacker after a breach at the vendor, or a malicious app the user approved; Tiddly admits any CIMD client and keeps DCR open.

**What the code already has.** `decode_clerk_jwt` reads the header `typ` after signature verification, requires `client_id` on `at+jwt` tokens, and logs `clerk_oauth_token_accepted client_id=... sub=...` at INFO. It does not compare `client_id` to anything. `_authenticate_user` sets `request.state.request_context` with `auth_type` and `source`. The three auth dependencies (`get_current_user`, `get_current_user_session_only`, `get_current_user_ai`) all call `_authenticate_user` first; the first two then call `_apply_rate_limit`, and the AI routes charge their own bucket in `apply_ai_rate_limit` (`api/routers/ai.py`), which depends on `get_current_user_ai`, so authentication completes before any rate-limit check. FastAPI 0.129.0 puts the matched route in the ASGI scope (`APIRoute.matches` sets `child_scope["route"]`, read in `fastapi/routing.py`), so a dependency can read the route template from `request.scope["route"].path`. `core/rate_limit_config.py` already keys a policy on `(method, path)` pairs (`SENSITIVE_ENDPOINTS`).

**What a user sees after this change.** Nothing different in any connected app: every MCP tool keeps working, and existing connections keep working without re-authenticating, because a connector token is still accepted on every route the MCP servers call. Anyone who takes a connector token out of an app and calls the REST API directly gets 403 on everything outside the MCP surface. `tiddly login` followed by `tiddly mcp configure` still creates PATs.

## Conventions for every milestone

- **Railway and production Clerk are shared systems.** Show each variable change, deploy, or merge to Shane and wait for approval. Reading Railway logs and `clerk api` GETs need no approval.
- **Tokens never appear in commands, output, or notes.** Any manual call with a real token goes through a short script that reads the token from where the client stores it (Claude Code keeps its MCP OAuth tokens in the macOS Keychain; verify on the machine), sends the request, and prints only the HTTP status, the `error_code` field, and presence booleans. No token value goes into a shell argument, stdout, or this file. This is the convention from the CIMD plan.
- **Shane is present for every browser sign-in** (Claude Code authentication, `tiddly login`). Those steps are marked.
- **Never remove or weaken a test to make the suite pass.** The policy test near line 477 of `backend/tests/core/test_auth_clerk.py` changes to the new policy; it is not deleted.
- **Each milestone ends green:** `make backend-verify` passes, and the milestone's own tests pass.
- **Prove it works.** Before calling a milestone done, run the feature the way a user would and look at the result, not a proxy: check the database row, the HTTP status, the log line. A new test counts only after it has been seen to fail on a known-bad input (for a 403 test, run it once against the pre-change code or with the allowlist entry removed). Review the real diff and output of any delegated work, not its summary. When a check passes too easily, suspect the check.
- **Record evidence in this plan.** Each milestone gets a dated "Results" section after its definition of done: the commands run, the status codes and log lines observed, and one row per client checked.

## Milestone 1: The API knows which OAuth tokens are the CLI's, and says so in the log

### Goal and outcome

The backend can tell the CLI's OAuth token from a connector's, using the signed `client_id` and a per-environment setting, and the accepted-token log line reports which it saw. Nothing is blocked yet, so this milestone can deploy to production as a check that the setting's value is right.

- The api service refuses to boot in real-auth mode when `CLERK_CLI_OAUTH_CLIENT_ID` is missing, with a message naming the variable. Dev mode (`VITE_DEV_MODE=true`) needs nothing.
- A request authenticated with the CLI's OAuth token writes `clerk_oauth_token_accepted client_id=... sub=... kind=cli`. A connector's token writes `kind=connector`.
- The request context carries the verified `client_id` and the CLI-or-connector classification for every OAuth access token, and nothing for session tokens and PATs. `auth_type` is unchanged (`session` for both OAuth kinds).
- Every existing test passes, with the fixtures that build `Settings` or a `MagicMock(spec=Settings)` updated to carry the new field.

### Implementation outline

1. **Setting.** Add `clerk_cli_oauth_client_id: str = Field(default="", validation_alias="CLERK_CLI_OAUTH_CLIENT_ID")` to `Settings` in `core/config.py`, with a comment saying it is the `client_id` of the pre-registered "Tiddly CLI" OAuth application on this environment's Clerk instance (production: the value of `prodOAuthClientID` in `cli/internal/auth/pkce_flow.go`; dev: the dev-instance app's ID, the same value the CLI gets through `TIDDLY_OAUTH_CLIENT_ID`), and that a missing value fails the API's boot rather than demoting the CLI's token.
2. **Startup check.** In `lifespan` in `api/main.py`, when `dev_mode` is false and the value is empty, raise with a message naming `CLERK_CLI_OAUTH_CLIENT_ID` and what breaks without it. Not in `Settings.validate_settings` (see Decided). Test clients that use `ASGITransport` do not run lifespan, so the existing fixtures that construct `Settings(dev_mode=False, ...)` are unaffected by the check, but they must still set the new field wherever a test authenticates with an OAuth token.
3. **Classification.** `decode_clerk_jwt` already knows whether the token is an OAuth access token (the header `typ` check) and its `client_id`. Expose both to `_authenticate_user` rather than re-deriving the header there; the return shape is the implementer's choice, with the existing `decode_clerk_jwt` tests as the constraint. In `_authenticate_user`, an OAuth access token whose `client_id` equals `settings.clerk_cli_oauth_client_id` (exact string compare) is the CLI's; any other OAuth access token is a connector's. Session tokens, PATs, and dev mode get no classification. Rewrite the `client_id` policy paragraph in `decode_clerk_jwt`'s docstring, which today records "there is no client-id allowlist" as an M4 decision: the CLI's ID is now compared to a setting, and connector IDs are still not allowlisted but are limited (Milestone 2).
4. **Request context.** Add to `RequestContext` the verified `client_id` and the classification for OAuth access tokens (both `None` otherwise). `AuthType` and `auth_type` persistence in `services/history_service.py` do not change (Decided, Shane 2026-11-03).
5. **Log line.** Append `kind=cli` or `kind=connector` to the existing `clerk_oauth_token_accepted` line. The classification happens where the setting is available; if that is `_authenticate_user` rather than `decode_clerk_jwt`, move the log call there so the line stays one line. The line is emitted once per OAuth-authenticated request (the CIMD plan records that as intended at beta scale).
6. **Docs for the setting** (code-adjacent, so they ship with the code): `.env.example` (a commented `CLERK_CLI_OAUTH_CLIENT_ID=` under the Clerk block, needed only when `VITE_DEV_MODE=false`), `README_DEPLOY.md` Step 5 API Service Variables (api service only, not the crons; stage it before merging because the deploy is on merge and the boot check fails without it), and the Step 6 Clerk checklist.

## Known limitations

- **What a connector token can still do.** It can read all of a user's bookmarks, notes, and prompts, create items, link them, and overwrite any item's content through the edit routes (the full-replace `PATCH` and `str-replace`), because those are the MCP tools. Through the same `PATCH` routes it can also archive any item and unarchive bookmarks and notes (`archived_at`; `PATCH /prompts/name/{name}` finds active prompts only, so an archived prompt returns 404 and is unarchived in the web app) and replace an item's links (`relationships`, where `[]` removes them all), because the routes accept those fields even though the MCP tools never send them; a direct API caller holding the token can do this, an app using only its tools cannot. Archiving hides an item from MCP search and the web app's default lists and is undone from the web app. An overwrite and a link change are each recorded as a new version, and the web app can restore the earlier version, content and links together, only while that earlier version's own history row exists: `reconstruct_content_at_version` (`services/history_service.py`) reports not-found without it, and the restore route (`api/routers/history.py`) returns 404 "Version not found". The retention rule, read in `frontend/src/content/data/tiers.json`, `tasks/cleanup.py`, and `services/history_service.py`: the daily cleanup deletes history rows older than the tier's `history_retention_days` (1 day free, 5 standard, 15 pro) but always keeps the most recent versioned row per item; every tier also prunes the oldest rows once an item passes 100 versions (`max_history_per_entity`), so an attacker making 100 or more edits to one item destroys its recoverable history. The connector's own change creates the newer row that makes the earlier one deletable, so on the free tier an item last edited more than a day ago stops being restorable at the next daily cleanup after a connector overwrites it or replaces its links. After that row is gone, the old content is still visible in the newer version's diff view, which derives it from that version's reverse diff, and a person can copy it back by hand; the one-click restore no longer brings it back, and the old links are not shown anywhere. The limit prevents deleting items (soft or permanent), publishing an item to a public link, restoring versions or trashed items, creating credentials, changing account settings, and spending on AI.
- **The CLI's token keeps full access.** A stolen CLI OAuth token can do everything for up to 24 hours, as today. The CLI is a first-party public client; limiting it is a different threat model.
- **A local program can get the CLI's access by running the CLI's own login flow.** The CLI is a public OAuth client: its client ID ships in the binary (`cli/internal/auth/pkce_flow.go`), and its Clerk application accepts a loopback redirect on any port, so any program on the user's machine can open the same browser sign-in and receive a token the backend classifies as the CLI's. The only barrier is the consent screen, which names "Tiddly CLI" (Clerk forces it on every OAuth flow on the instance, recorded in the CIMD plan's Known limitations). Remote connectors cannot do this, because Clerk sends the code to the user's own machine. The limit protects against what a connector token can do, not against a malicious program on the user's own machine.
- **PATs a connector created before enforcement stay valid.** If a connector token was ever used to mint a PAT, that PAT keeps full access after this change, and nothing records which PATs came from a connector: `models/api_token.py` stores no originating credential, and the accepted-token log line only reached Railway from 2026-10. A user can only review their token list by name in Settings → Personal Access Tokens.
- **The classification is per vendor, not per installation.** Every Claude Code installation presents the same `client_id`. The limit protects against what any holder of a connector token can do, not against one specific installation.
- **Rate limits and quotas are unchanged.** A connector token on an allowed route consumes the user's normal read and write buckets, as today.
- **Dev mode never classifies.** With `VITE_DEV_MODE=true`, authentication is bypassed and the check never runs, so the evals and the dev-mode test suite cannot catch a regression here; the real-auth tests in Milestone 2 are the coverage.
- **The drift guard covers the branches its representative calls reach.** A new code path inside an existing tool that calls a new route is caught only when the test's call table reaches it; the Milestone 2 dev run with real clients is the independent check.
